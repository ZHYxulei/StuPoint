# StuPoint 安全审计、业务整改与 shadcn/ui 全站统一设计

## 1. 背景与目标

StuPoint 是基于 Laravel 13、Inertia v3、React 19 与 Tailwind CSS v4 的学生积分管理系统。项目已经使用 shadcn/ui New York 风格、Radix primitives、语义化 CSS 变量和本地 `resources/js/components/ui` 组件层。因此，本项目不是从零安装 shadcn/ui，而是在现有基座上完成安全审计、实质问题整改和全站视觉收口。

本次工作目标：

1. 系统检查权限、安全、数据一致性、业务逻辑、代码结构和验证能力。
2. 修复所有已确认的实质问题，不限于最高风险漏洞。
3. 保留并加固插件系统。
4. 完善家长绑定、积分、商城订单和验证码生命周期。
5. 将约 69 个 React 页面统一到“克制校园”shadcn/ui 设计系统。
6. 允许改善筛选、分页、反馈和导航交互，但不随意改变既定业务规则。
7. 为整改和迁移建立可重复的自动化与端到端验证证据。

## 2. 已确认的项目现状

### 2.1 技术与 UI 基座

- `components.json` 已配置 shadcn/ui New York、TypeScript、CSS variables、Lucide 和 `@/components/ui` 别名。
- `resources/css/app.css` 已包含完整的明暗模式、侧边栏 token 和多主题色系统。
- 主应用侧边栏、认证页和多数后台 CRUD 已经使用本地 shadcn/ui primitive。
- 主要遗留区域是安装向导、部分公共页、原生表格、重复错误/分页组件以及页面内硬编码色彩。
- 项目存在约 69 个 Inertia React 页面，覆盖后台、认证、安装、家长端、学生会、商城、积分和公共页面。

### 2.2 验证基线

现有仓库具备 Pest、PHPUnit、Pint、TypeScript、ESLint、Prettier、客户端构建和 SSR 构建能力，但默认验证入口不完整：

- PHP 测试只覆盖少数业务路径。
- CI 未稳定执行 TypeScript 和 SSR 构建。
- 前端 lint 脚本是写入式 `--fix`，不适合作为纯验证门禁。
- 没有浏览器 E2E、自动化无障碍检查和视觉回归。
- 测试使用 SQLite 内存库，而生产数据库为 MySQL，需要为关键并发和数据库语义增加 MySQL 验证。

### 2.3 重点风险面

实施前必须用回归测试或可重复验证确认以下高风险候选：

- 后台和 API 动作级授权不足、角色提升及 Web/API 权限漂移。
- 插件 ZIP 解压、自动发现、启停、卸载和运行时 boot 边界不安全。
- 家长仅凭学号自动绑定学生，可能导致学生数据越权访问。
- 积分首次建账和并发增减存在唯一键竞争、丢更新及余额/流水不一致风险。
- 商城 `quantity` 参数没有完整进入订单、积分和库存计算。
- 订单取消或失败缺少可靠的积分退款和库存回补。
- 验证码可重放、用途隔离不足、发送失败后残留及敏感日志问题。
- 订单核销使用登录密码或其他过度敏感凭据，且状态历史可能失真。

## 3. 总体方案

采用“安全优先分阶段”路线，避免业务修复与大规模 UI 迁移互相干扰。

### 阶段一：基线与缺陷确认

1. 运行 PHP/Pest、Pint、TypeScript、Prettier、只读 ESLint、客户端构建和 SSR 构建。
2. 记录现有失败，不把历史问题误归因于本次改动。
3. 为每个高风险候选建立最小失败回归测试或安全复现。
4. 只有确认行为与影响后才进入修复。

### 阶段二：安全与业务整改

集中修复授权、插件、家长绑定、积分、订单和验证码等实质问题，不混入全站视觉迁移。

### 阶段三：设计系统收口

保留现有 shadcn/ui 和主题基座，统一 primitive、组合组件、页面壳、状态反馈、表格、分页、响应式和无障碍规范。

### 阶段四：全站分批迁移

迁移顺序：

1. 已大体采用 shadcn/ui 的低风险 CRUD 与表单页。
2. 公共导航、公共页、认证和设置布局。
3. 订单、系统设置等复杂后台页。
4. 独立且遗留程度最高的安装向导。

### 阶段五：综合验证与收尾

每批执行静态检查、构建、后端回归和关键浏览器流程。最后做权限、安全、无障碍、响应式和视觉一致性复核。

## 4. 安全与业务整改设计

### 4.1 授权模型

建立明确的角色—能力矩阵：

- 路由中间件只负责粗粒度入口保护。
- Policy、Gate 或专用授权服务负责资源和动作级判断。
- Web 控制器与 API 控制器复用同一授权规则。
- 前端隐藏按钮不作为安全边界。
- 非超级管理员不得授予高于自身的角色，也不得修改受保护账号。
- 插件管理、系统设置及其他高危动作仅授予明确角色。
- 班主任、年级负责人和家长只能访问所属范围内的数据。

授权失败统一返回 403，并确保不会先执行写入再失败。

### 4.2 插件系统加固

保留插件能力，但将插件视为受信任代码部署面，而不是普通内容上传。

上传与安装：

- 安装入口仅限明确授权角色。
- 在解压前规范化 ZIP 条目路径，拒绝 `..`、绝对路径、驱动器路径、符号链接和目标目录外写入。
- 校验插件清单、命名空间、入口类、允许的扩展名、文件数量与解压大小。
- 先解压到隔离临时目录，完成全部验证后再原子移动到插件目录。
- 安装、迁移及依赖处理失败时回滚数据库状态和临时文件。

运行时：

- Provider 只加载数据库中已安装且 `enabled` 的插件。
- 单纯存在于 `plugins/` 目录的代码不得自动注册或 boot。
- 禁用操作必须在下一请求立即停止加载。
- 卸载需明确处理运行状态、数据迁移、代码目录和失败回滚；不得出现“数据库已卸载但代码继续执行”。
- 安装、启用、禁用、配置和卸载记录操作者、插件版本、结果和时间，但不记录秘密配置。

### 4.3 家长绑定

采用“学号 + 短期单次邀请码”，并提供可配置的班主任复核开关。

- 邀请码由有权限的管理员或班主任为特定学生生成。
- 邀请码绑定学生、用途、过期时间和消费状态，不可跨学生或重复使用。
- 复核关闭时，正确验证后立即建立 approved 关系。
- 复核开启时，正确验证后建立 pending 关系；班主任仅能审核自己班级的学生。
- pending、rejected、expired 关系不能读取学生积分、交易或订单。
- 所有 Web/API 数据查询都必须通过已批准的家长—学生关系授权。

### 4.4 积分一致性

所有积分写操作必须统一进入 `PointService` 或清晰拆分的积分领域服务。

- 在数据库事务中锁定用户积分账户。
- 首次建账要处理并发唯一键竞争，不允许产生重复账户。
- 增减余额、可兑换积分和写入流水在同一事务完成。
- 禁止余额降到业务规则允许值以下。
- 快速评分、人工调分、商城兑换和订单补偿不得各自复制积分逻辑。
- 为写操作保留来源、操作者、业务对象和幂等键等可审计元数据。

### 4.5 订单数量与状态机

正式支持多件兑换：

- `orders` 持久化 `quantity`。
- 单价/积分成本使用订单创建时的快照。
- 总积分与库存变化按 `quantity` 计算。
- API、Web 页面、资源类和数据库字段保持一致。
- 库存检查和扣减在事务与行锁中完成。

定义显式订单状态机：

- 仅允许列明的状态迁移，拒绝任意跳转。
- 核销完成只能执行一次。
- 合法取消或失败自动、幂等地退还积分并回补库存。
- 补偿使用唯一业务键或补偿状态，重复请求不得重复退款。
- 状态历史必须记录真实的 `from_status`、`to_status`、操作者、原因和时间。
- 外部兑换需要额外记录第三方请求状态和补偿结果。

### 4.6 验证码与核销凭据

- 验证码按手机号/主体、用途和会话隔离。
- 具备明确的过期、尝试次数、限流和单次消费语义。
- 发送失败时不保留可用验证码。
- 验证成功后原子标记消费，防止并发重放。
- 生产环境禁止使用自动放行的验证码提供者。
- 日志不得记录短信验证码、订单核销码、登录密码、身份证输入或完整秘密配置。
- 订单核销不再接受用户登录密码作为核销凭据。
- 核销采用专用短期码或明确批准的业务身份验证方式。

## 5. 应用架构与数据流

### 5.1 前端提交

- Inertia v3 页面优先使用 `<Form>`、`useForm` 或适合的 `useHttp` 能力。
- 路由链接和提交目标使用 Wayfinder 生成函数或命名路由封装。
- 页面依赖 `@/components/ui/*` primitive 和少量领域组合组件，不直接依赖 Radix primitive。
- 表单、列表、确认对话框、筛选和分页使用统一 API 与状态反馈。

### 5.2 后端边界

- Form Request：输入格式和业务前置验证。
- Policy/Gate：身份、角色、资源归属和动作授权。
- Controller：请求编排、调用服务、返回 Inertia/API 响应。
- Domain Service：事务、状态机、并发、幂等和跨模型业务规则。
- Model：关系、casts、查询范围和有限的实体行为，不承载大型流程。
- API Resource：稳定输出契约，不输出不存在或未定义的字段。

Web 与 API 必须共享领域服务、授权和状态规则，避免入口之间行为漂移。

## 6. 错误处理

- 字段验证错误显示在对应控件下方，并保留用户输入。
- 权限错误统一返回 403 页面或 API 错误结构。
- 资源不存在使用 404。
- 当前状态不允许操作、库存冲突和重复操作使用明确的领域错误；API 可使用 409。
- 短信、邮件、第三方兑换和插件安装失败不得留下半完成业务状态。
- 危险操作使用 `AlertDialog`，明确说明影响且避免误触。
- 成功、失败、空状态和加载状态采用统一组件。
- 用户可见错误不包含堆栈、SQL、路径、秘密和敏感输入。

## 7. “克制校园”设计系统

### 7.1 视觉方向

- 中性背景、低饱和主题色和清晰信息层级。
- 默认使用沉静绿灰基调，但保留现有多主题选择和明暗模式。
- 避免公共页和统计卡片中的大面积炫彩渐变。
- 统一 8–10px 圆角、克制阴影、清晰边框和适中的后台信息密度。
- 色彩表达状态时同时提供文本或图标，不把颜色作为唯一信息通道。

### 7.2 Token 与 primitive

保留并整理现有：

- `resources/css/app.css` 语义 token。
- `components.json` shadcn CLI 配置。
- `resources/js/components/ui` 本地 primitive。
- 主应用侧边栏和主题切换链路。

所有页面使用 `background`、`foreground`、`card`、`muted`、`primary`、`destructive`、`border`、`sidebar` 等语义 token。页面中不散落无必要的固定灰、蓝、绿、紫色值。

### 7.3 组件收口

- 合并重复的 `InputError`，形成字段错误和全局错误两种明确形态。
- 使用 `ui/pagination` 作为底层，业务分页只做数据适配。
- 表格统一基于 `ui/table`；桌面为表格，小屏为卡片列表或适合的横向滚动模式。
- Link/Button 统一使用 `Button asChild` 等正确语义。
- 统一 Badge 状态映射、空状态、Skeleton、加载 Spinner、Alert 和 AlertDialog。
- 公共导航拆分共享导航数据、登录态操作和移动/桌面呈现，减少重复。
- 复杂订单核销和设置分区拆为独立、可测试的组合组件。

### 7.4 页面壳与响应式

- 登录后继续使用统一侧边栏应用壳。
- 认证页面统一到单一主布局，未使用的备选布局要么删除，要么明确用途。
- 公共页使用统一 Public Layout，而不是每页重复导航和容器。
- 安装向导使用统一 Install Layout、步骤指示、Card 和标准表单控件。
- 设置页面在移动端使用 Tabs、Select 或 Sheet，不保留固定宽度侧栏挤压内容。
- 菜单、弹窗、表单、分页和切换控件具备正确的 label、ARIA 状态、焦点管理和键盘操作。

## 8. UI 迁移批次

### 批次一：设计系统收口

- 合并重复错误和分页组件。
- 统一 Link/Button、Badge 和状态反馈。
- 建立页面容器、页头、筛选栏、数据列表、表单区和空状态组合模式。

### 批次二：低风险页面

- 已经大体使用 shadcn/ui 的 CRUD、认证、积分、商城和学生会表单页。
- 统一间距、层级、错误状态、按钮顺序和响应式。

### 批次三：布局与公共体验

- 公共导航、欢迎页、排行榜、关于页。
- 设置布局、认证布局和其他重复页面壳。
- 允许改善筛选、分页、反馈和导航，但保持业务路由与核心操作语义。

### 批次四：复杂后台

- 订单列表、详情和核销。
- 系统设置大页面。
- 用户、审批、插件等高密度管理页面。
- 在迁移 UI 的同时只做与边界拆分直接相关的结构整理，不开展无关重构。

### 批次五：安装向导

- 全部原生输入、选择、单选和按钮迁移为标准组件。
- 统一步骤、验证、错误、前后导航和完成页。
- 保留安装过程所需的传统表单提交或特殊会话逻辑，不强行套用不适合的 Inertia 模式。

## 9. 测试与验证策略

### 9.1 缺陷回归

对确认的问题采用失败测试先行：

- 角色—动作—资源范围权限矩阵。
- 低权限角色不能修改角色、积分、插件和订单。
- 家长不能查看未批准或不属于自己的学生。
- 邀请码过期、重放、跨学生和可选复核。
- 插件 Zip Slip、禁用后停止 boot、卸载后停止运行。
- 积分首次建账和并发增减。
- 多件订单积分/库存计算。
- 取消/失败补偿的幂等性。
- 验证码过期、限流、用途隔离、单次消费和发送失败。
- 核销状态历史及敏感日志清理。

### 9.2 每批静态验证

- `vendor/bin/pint --dirty --format agent`：修改 PHP 后格式化。
- 相关 Pest 测试，再运行完整 `php artisan test --compact`。
- `npm run types`。
- `npm run format:check`。
- 只读 ESLint 命令，不使用 `--fix` 作为验证。
- `npm run build`。
- `npm run build:ssr`。

### 9.3 浏览器与无障碍验证

关键流程：

1. 登录、注册、找回密码、双因素认证。
2. 积分概览和历史。
3. 商城多件下单、订单详情和取消结果。
4. 家长邀请码绑定与可选班主任复核。
5. 后台审批、快速评分和订单核销。
6. 插件上传、启停和卸载的授权与反馈。
7. 系统设置和安装向导。

对这些流程检查：

- 桌面与移动视口。
- 键盘操作与焦点顺序。
- 表单 label、错误关联和弹窗焦点管理。
- 页面无控制台错误和网络异常。
- 主要页面无明显布局溢出、遮挡和主题对比度问题。

### 9.4 数据库兼容性

SQLite 继续用于快速测试，但以下测试需在 MySQL 环境补充验证：

- 行锁和并发积分更新。
- 库存扣减与订单补偿。
- 唯一键冲突和幂等键。
- 迁移、外键和索引行为。

## 10. 完成标准

工作只有同时满足以下条件才算完成：

1. 所有审计发现都有“已确认并修复”“确认不成立”或“明确接受风险”的结论。
2. 已修实质问题均有回归证据。
3. Web 与 API 对同一业务使用一致的授权和领域规则。
4. 插件禁用/卸载后不会继续加载，上传路径无法越出目标目录。
5. 家长只有通过邀请码和必要复核后才能访问学生数据。
6. 积分余额、流水、订单数量、库存和取消补偿保持一致。
7. 验证码不可重放，日志不包含敏感凭据。
8. 全站页面遵守统一 shadcn/ui 设计系统边界。
9. PHP 测试、TypeScript、只读静态检查、客户端与 SSR 构建通过。
10. 关键浏览器流程、移动响应式和无障碍检查通过。

## 11. 非目标与约束

- 不更换 Laravel、Inertia、React、Tailwind 或 shadcn/ui 技术栈。
- 不把项目改造成全新的产品流程或重新定义学校业务制度。
- 不为视觉迁移引入不必要依赖。
- 不开展与本次安全整改或 UI 边界无关的大规模重构。
- 不将 `.superpowers/` 或其他 Superpowers 临时工作目录提交或上传；这些目录保持本地忽略。
- 当前用户已有的 `package.json` 未提交改动不属于本设计，实施时不得覆盖或擅自纳入提交。
